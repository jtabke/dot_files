Decision brief · Linux · macOS · WSL2

Dotfiles, without the drift.

A portable source of truth that supports edits in either direction, installs tools by platform, and keeps secrets out of Git.

Prepared from the current 69-file repository and its live deployment state.

01 · Current state

The files are organized by memory, not by a deployment contract.

01

Mixed destinations

Root dotfiles, XDG trees, app folders, and special paths such as ~/.config/aerospace/aerospace.toml coexist without one mapping.

02

Manual drift

Most sampled live files differ from the repository. The README deploys only Pi and Hyprland files.

03

Platform leakage

WSL2 is treated as generic Linux. macOS and Linux desktop behavior sits inside shared shell startup files.

Root problem: there is no declared owner, destination, platform profile, conflict policy, or repeatable update path for each file.

02 · What good looks like

Six tests for the new system.

Portable

First-class profiles for macOS, Linux desktop variants, and WSL2—not just an OSTYPE branch.

Bidirectional

Edit the source and apply it, or edit the live file and review/import the change.

Selective

Install only files and tools that match OS, host role, graphical stack, and optional features.

Safe

Preview diffs, avoid blind overwrite, keep secrets external, and preserve local/runtime files.

Bootstrap-aware

Install or verify packages with Homebrew and selected Linux package managers.

Low entropy

Prefer one established tool over a custom framework that this repository must maintain forever.

03 · The field

Six viable approaches. Different centers of gravity.

Best overall fitcopy/apply

chezmoi

Center: cross-platform convergence.

  • Templates and OS/host data are built in.
  • diff, apply, add, and merge support both edit directions.
  • Password-manager integrations and WSL detection are native concepts.
  • Run-on-change scripts can bootstrap packages.

Cost: special source names and Go-template syntax; careless templates can become complex.

bare Gitcopy/link

yadm

Center: Git-native dotfile tracking.

  • Files remain close to their real home paths.
  • Alternates and templates handle host/OS variants.
  • Bootstrap scripts and encrypted files are supported.
  • Low conceptual jump for Git users.

Cost: weaker package orchestration and conflict workflow; alternate-file proliferation is easy.

symlink farmvery simple

GNU Stow

Center: deterministic symlinks.

  • Tiny mental model and transparent live edits.
  • Package folders can represent common/macOS/Linux/WSL groups.
  • Conflicts are visible instead of silently overwritten.

Cost: no native templates, secrets, package install, or host data. Bidirectional edits work because live files point into the clone.

declarative linksPython

Dotbot

Center: a readable install manifest.

  • Links, cleanup, shell actions, defaults, and condition commands.
  • Easy to add to an existing repository.
  • Plugin ecosystem can extend behavior.

Cost: source-to-live import, rich templating, package models, and secret integration become scripts or plugins.

fully declarativelarge adoption

Home Manager

Center: reproducible user environments through Nix.

  • Packages, programs, files, variables, and services share one model.
  • Strong rollback and reproducibility story.
  • Works standalone on Linux, WSL, and macOS with Nix.

Cost: Nix language and ecosystem become foundational. Live-file import is not the natural workflow.

maximum controlmaximum upkeep

Custom installer

Center: exactly this repository.

  • Any mapping, UI, package policy, or exception is possible.
  • No manager-specific file naming.

Cost: we own detection, backups, merge safety, idempotence, secrets, package adapters, testing, and future portability.

05 · Recommendation

Use chezmoi as the file manager. Keep package logic thin and explicit.

This gives the repository a mature convergence engine without turning every config into a template or pretending package names are portable.

Source state

Shared files stay plain. Only values or blocks that vary become templates.

→

Host data

OS, WSL, role, desktop stack, package manager, and app choices select behavior.

→

Target state

Preview with chezmoi --source /path/to/dot_files diff, then apply exact files and run changed bootstrap steps.

.
├── .chezmoiroot                    # points chezmoi at home/
├── home/
│   ├── .chezmoi.toml.tmpl          # once-only role/desktop/package prompts
│   ├── .chezmoiignore               # decoded target profile exclusions
│   ├── run_onchange_install-packages.sh.tmpl
│   ├── dot_zshenv
│   ├── dot_config/                 # zsh, nvim, Kitty, and desktop trees
│   │   └── aerospace/aerospace.toml # macOS profile only
│   └── dot_pi/agent/               # one managed Pi tree
├── .pi/agent -> home/dot_pi/agent  # project metadata link
└── docs/
Important constraint: templates are a scalpel, not the default. Prefer whole-file profile selection and sourced fragments over conditionals scattered through large config files.

06 · Daily workflow

Both edit directions stay reviewable.

Repository first

Edit source → preview → apply

chezmoi --source /path/to/dot_files cd
$EDITOR home/dot_config/zsh/dot_zshrc
chezmoi --source /path/to/dot_files diff
chezmoi --source /path/to/dot_files apply
Live first

Edit target → inspect → import

$EDITOR ~/.config/zsh/.zshrc
chezmoi --source /path/to/dot_files diff
chezmoi --source /path/to/dot_files re-add ~/.config/zsh/.zshrc
git -C /path/to/dot_files diff

For templated files, use chezmoi --source /path/to/dot_files merge or edit the source template. Do not blindly overwrite a template from rendered output.

07 · Portability model

Model capabilities, not a growing list of hostnames.

Base

zsh core, Git defaults, tmux, Neovim, Pi, npm/Bun/uv policy.

Platform

macos, linux, or wsl. WSL is never inferred as a normal Linux desktop.

Role

workstation or shell.

Desktop

hyprland, aerospace, or none.

Features

ROCm, auto-tmux, GUI apps, Git LFS, work identity, notes paths.

Private data

Git identity and tokens resolve from the selected external secret manager at apply time.

08 · Migration

Move in small, reversible slices.

1

Inventory and freeze

Declare every source → destination mapping. Back up current live files. Decide which side wins for each existing drift.

2

Adopt shared CLI configs

Bring in Git, zsh, tmux, Neovim, terminal, package-manager, and Pi files. Add diff/apply checks.

3

Split shell policy

Separate portable shell core from macOS, Linux desktop, WSL, local paths, and auto-tmux behavior.

4

Add desktop profiles

Migrate Hyprland, AeroSpace, and SketchyBar as mutually selected capabilities.

5

Add package adapters

Start with Homebrew plus only the Linux distributions actually used. Unsupported distros get a dependency report, not guesses.

6

Prove portability

Test clean apply, second-run idempotence, live re-import, secret absence, and WSL desktop exclusion in disposable homes or containers.

First milestone: one safe command can preview and deploy the shared shell/editor/tool layer on the current Linux host without touching desktop-specific or runtime files.

09 · Decision gate

Choose the operating model before moving files.

Recommended

Proceed with a chezmoi proof of concept

Migrate zsh, Git, tmux, and one terminal config first. Demonstrate both edit directions and Linux/macOS/WSL rendering before moving desktop configs.

Fallback

Use Stow if templates are rejected

Accept more duplicated platform packages and use external scripts for packages/secrets in exchange for a nearly trivial symlink model.

Do not build a custom manager unless a proof of concept exposes a requirement that established tools cannot satisfy.
